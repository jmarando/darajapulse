Campaign email brand resolution lives in `supabase/functions/_shared/campaign-brand.ts` and is imported by the dashboard and review function, so both sending paths choose the same template and identity without cross-brand fallback.
OMO payments use campaign roster fee/count and approved draft IDs, while Royco retains view tiers, because the two contracts have distinct payment rules.
Contract dates are additive display/reporting fields, never implicit payment filters, so historical eligibility survives agreement corrections.
Agreement amendments and their signatures use separate tables linked to immutable original signatures, so existing submission and payment gates remain unchanged.
Amended PDFs are generated from signed text snapshots into private storage and dispatched on signing, so signatures never attach to revised wording retroactively.
Edge functions that spend credits, send email or cross tenants check their caller with `supabase/functions/_shared/auth.ts` (scheduled job key, service role, or staff role), and cron jobs call them through `public.invoke_job_function`, because `verify_jwt` accepts the public anon key.
Campaign peak-metric readers exclude aggregate rows without collection timestamps, because posts with no snapshots must remain missing rather than appear freshly synced.
The `groundwork-*` functions work only in the agency named by the `GROUNDWORK_AGENCY_SLUG` secret and answer 503 when it is missing or wrong, never falling back to another agency, because their job key must not reach other tenants' data; their checks and row shapes live in `supabase/functions/_shared/groundwork-link.ts` so tests can run them without Deno.
Listening's morning view is worked out by one pure module, `supabase/functions/_shared/listening-brief.ts`, that the page imports and the alert emails will import too, so the two cannot disagree; a post with no view count (Instagram, Reddit) is never read as 0 views and is not judged on spread, because a missing number is not a quiet post.
Listening's alert emails come from the same module and are sent hourly by `listening-alerts`; `listening_alert_log` keeps one row per brand and alert key because the job reads the same posts again, and a row is written only after every recipient was handled, so a failed send is retried instead of forgotten.
